## Reminder Preferences

### POST `/api/vaults/{vault_id}/reminder-preferences`

Create or update reminder preferences for a vault.

**Path Parameters**

| Name       | Type   | Description          |
|------------|--------|----------------------|
| `vault_id` | uint64 | On-chain vault ID    |

**Request Body** (`application/json`)

| Field                  | Type            | Required | Description                                              |
|------------------------|-----------------|----------|----------------------------------------------------------|
| `channels`             | array of string | Yes      | One or more of: `"email"`, `"sms"`, `"push"`            |
| `hours_before_expiry`  | integer (> 0)   | Yes      | Hours before TTL expiry to send the first reminder       |
| `frequency`            | string          | Yes      | How often to repeat: `"once"`, `"daily"`, `"hourly"`    |
| `timezone`             | string          | No       | IANA zone for the 09:00 local reminder time (default `"UTC"`) |

**Example Request**

```json
{
  "channels": ["email", "sms"],
  "hours_before_expiry": 48,
  "frequency": "daily",
  "timezone": "America/New_York"
}
```

**Responses**

| Status | Description                              |
|--------|------------------------------------------|
| 200    | Preferences saved; returns saved object  |
| 422    | Validation error (empty channels, zero hours) |
| 500    | Internal server error                    |

**Example Response (200)**

```json
{
  "vault_id": 42,
  "channels": ["email", "sms"],
  "hours_before_expiry": 48,
  "frequency": "daily"
}
```

## Two-Factor Authentication

Per-vault two-factor authentication is implemented in `backend/src/two_factor.rs`.
Every 2FA endpoint is scoped to a single vault under `/api/vaults/{vault_id}/2fa`
and is identified by the on-chain vault ID in the path. Configuration is persisted
per vault in the backend database; the TOTP secret is never stored in plaintext
(see [Configuration](#configuration) below).

> **Implementation note (issue #2108):** the handlers documented here are the set
> currently implemented in `two_factor.rs`: `status`, `enable`, `verify`, and
> `rotate-key`. A dedicated disable (`DELETE .../2fa`) endpoint and single-use
> TOTP **backup codes** (`GET .../2fa/backup-codes`,
> `POST .../2fa/regenerate-backup-codes`) are **not yet implemented**; when they
> land they will be documented in this section.

### Endpoint summary

| Endpoint | Purpose | Current implementation |
|----------|---------|------------------------|
| `POST /auth/2fa/setup` | Begin TOTP/SMS/email enrolment and return a TOTP secret or provisioning URI | Use `POST /api/vaults/{vault_id}/2fa/enable` in the current backend |
| `POST /auth/2fa/verify` | Verify a TOTP or pending SMS/email code | Use `POST /api/vaults/{vault_id}/2fa/verify` in the current backend |
| `POST /auth/2fa/disable` | Disable 2FA and clear the current session verification | Not implemented |
| `GET /auth/2fa/backup-codes` | List or report remaining single-use TOTP recovery codes | Not implemented |
| `POST /auth/2fa/regenerate-backup-codes` | Replace the backup-code set | Not implemented |

The `/auth/2fa/*` names above describe the public API contract. The vault
scoped routes currently implemented in `two_factor.rs` are
`/api/vaults/{vault_id}/2fa/{status,enable,verify,rotate-key}`. Until dedicated
disable and backup-code handlers exist, clients must not rely on those two
endpoint families.

### Supported methods

| Method  | Code delivery                                             | Code lifetime             | Verification                       |
|---------|----------------------------------------------------------|---------------------------|------------------------------------|
| `totp`  | RFC 6238 TOTP generated by an authenticator app         | 30 s time step, one-time  | HMAC-SHA1, 6 digits, replay-protected |
| `sms`   | Server-generated 6-digit OTP sent to the vault's phone  | 5 minutes (300 s)         | Single-use, in-memory pending store |
| `email` | Server-generated 6-digit OTP sent to the vault's email  | 5 minutes (300 s)         | Single-use, in-memory pending store |

### GET `/api/vaults/{vault_id}/2fa/status`

Returns the current 2FA configuration and whether the vault is verified for the
current session. Defaults to `enabled: false` if 2FA was never configured.

**Path Parameters**

| Name       | Type   | Description       |
|------------|--------|-------------------|
| `vault_id` | uint64 | On-chain vault ID |

**Responses**

| Status | Description                                                        |
|--------|--------------------------------------------------------------------|
| 200    | Returns `TwoFactorStatusResponse`                                  |
| 500    | Database error (`{"code":"internal_error",...}`)                   |

**Example Response (200)**

```json
{
  "vault_id": "42",
  "enabled": true,
  "method": "totp",
  "verified": true,
  "phone": null,
  "email": null
}
```

### POST `/api/vaults/{vault_id}/2fa/enable`

Begins 2FA enrolment for the vault. The vault is **not** considered enabled until
the code is verified with `POST .../2fa/verify`.

- `totp`: generates a Base32 secret, persists only the encrypted form, and
  returns the plaintext secret **once** together with a provisioning URI for
  authenticator apps.
- `sms` / `email`: stores the destination contact and issues a verification code
  valid for 5 minutes (no secret is returned).

**Request Body** (`application/json`)

| Field    | Type   | Required      | Description                              |
|----------|--------|---------------|------------------------------------------|
| `method` | string | Yes           | One of: `"totp"`, `"sms"`, `"email"`     |
| `phone`  | string | For `sms`     | Destination phone number                 |
| `email`  | string | For `email`   | Destination email address                |

**Responses**

| Status | `code`           | Description                                                                          |
|--------|------------------|--------------------------------------------------------------------------------------|
| 200    | —                | Returns `Enable2FAResponse` (for `totp`: `secret` + `provisioning_uri`; for `sms`/`email` both are omitted) |
| 422    | `invalid_input`  | Missing `phone` (for `sms`) or `email` (for `email`), or an unknown method            |
| 500    | `internal_error` | `TOTP_ENCRYPTION_KEY` unset/under-length, or database error                          |

**Example Request**

```json
{ "method": "totp" }
```

**Example Response (200, totp)**

```json
{
  "vault_id": "42",
  "method": "totp",
  "secret": "JBSWY3DPEHPK3PXP",
  "provisioning_uri": "otpauth://totp/42?secret=JBSWY3DPEHPK3PXP&issuer=TTL-Legacy&algorithm=SHA1&digits=6&period=30"
}
```

For `sms` / `email` the response carries only `vault_id` and `method`.

### POST `/api/vaults/{vault_id}/2fa/verify`

Verifies a 2FA code and marks the vault's 2FA as enabled and verified for the
current session.

**Request Body** (`application/json`)

| Field  | Type   | Required | Description                                  |
|--------|--------|----------|----------------------------------------------|
| `code` | string | Yes      | TOTP code, or the SMS/email verification code |

**Responses**

| Status | `code`            | Description                                                                          |
|--------|-------------------|--------------------------------------------------------------------------------------|
| 200    | —                 | Code accepted; vault marked enabled + verified (empty response body)                |
| 401    | `unauthorized`    | Invalid or expired code (`message`: `"invalid 2FA code"`)                           |
| 404    | `not_found`       | 2FA is not configured for this vault                                                |
| 500    | `internal_error`  | Missing/unreadable TOTP secret, or `TOTP_ENCRYPTION_KEY` not configured              |

> A TOTP code is accepted only for the current time step and only once:
> replaying a code from an earlier (or the same) time step is rejected, and the
> latest consumed time step is tracked per vault.

### POST `/auth/2fa/disable`

Disables 2FA for the authenticated vault and removes the vault's verified
session state. A successful request should require the current 2FA code or a
current authenticated session, invalidate pending enrolment codes, and remove
stored TOTP or backup-code material.

**Status:** not implemented in `backend/src/two_factor.rs`.

**Planned Responses**

| Status | `code` | Description |
|--------|--------|-------------|
| 200 | — | 2FA disabled |
| 401 | `unauthorized` | Verification code or authenticated session is invalid |
| 404 | `not_found` | 2FA is not configured for the vault |
| 429 | `rate_limit_exceeded` | Per-client request quota exhausted |
| 500 | `internal_error` | Database or key-store failure |

### GET `/auth/2fa/backup-codes`

Returns metadata for the vault's remaining single-use TOTP backup codes. Backup
codes must be returned only when the owner is currently authenticated and
verified. The API should never expose stored plaintext codes after generation;
this endpoint must return code status/count metadata, not recoverable secrets.

**Status:** not implemented in `backend/src/two_factor.rs`.

**Planned Responses**

| Status | `code` | Description |
|--------|--------|-------------|
| 200 | — | Returns the remaining backup-code count and/or generation metadata |
| 401 | `unauthorized` | An authenticated 2FA session is required |
| 404 | `not_found` | 2FA or backup codes are not configured |
| 429 | `rate_limit_exceeded` | Per-client request quota exhausted |
| 500 | `internal_error` | Database or key-store failure |

---

### POST `/auth/2fa/regenerate-backup-codes`

Invalidates the current backup-code set and generates a fresh set for recovery
use. The plaintext replacement codes should be returned once and never persisted
in plaintext; each code is single-use and may be consumed only within the
configured method window.

**Status:** not implemented in `backend/src/two_factor.rs`.

**Planned Responses**

| Status | `code` | Description |
|--------|--------|-------------|
| 200 | — | Returns replacement backup codes once |
| 401 | `unauthorized` | An authenticated 2FA session is required |
| 404 | `not_found` | 2FA is not configured for the vault |
| 429 | `rate_limit_exceeded` | Per-client request quota exhausted |
| 500 | `internal_error` | Database or key-store failure |

### POST `/api/vaults/{vault_id}/2fa/rotate-key`

Re-encrypts the stored TOTP secret under the current `TOTP_ENCRYPTION_KEY`. Use
this during **encryption-key rotation**: set `TOTP_ENCRYPTION_KEY_PREVIOUS` to the
old key and `TOTP_ENCRYPTION_KEY` to the new key, then call this endpoint per
vault. The secret value is **unchanged** — the authenticator app keeps working
without re-enrolment; only the at-rest ciphertext changes.

**Request Body:** none.

**Responses**

| Status | `code`            | Description                                                  |
|--------|-------------------|--------------------------------------------------------------|
| 200    | —                 | Secret re-encrypted under the current key (empty body)      |
| 404    | `not_found`       | 2FA is not configured for this vault                        |
| 500    | `internal_error`  | Decryption failed, or `TOTP_ENCRYPTION_KEY` not configured |

### Configuration

The 2FA subsystem is configured via environment variables. None of these are
on-chain; they only affect the backend.

| Variable                        | Required for      | Description                                                                                                                                                                  |
|---------------------------------|-------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `TOTP_ENCRYPTION_KEY`           | TOTP enrol/verify | Symmetric key used to encrypt TOTP secrets at rest. Must be **>= 32 bytes**. Ciphertext uses the form `enc:v1:<nonce_hex>:<ciphertext_hex>`. If unset or too short, any TOTP read/write returns `500`. |
| `TOTP_ENCRYPTION_KEY_PREVIOUS`  | Key rotation      | The previous key, retained **only for decryption** during a `TOTP_ENCRYPTION_KEY` rotation. Decryption tries the current key first, then this one. Omit when not rotating.   |

#### TOTP parameters (fixed, RFC 6238)

| Parameter        | Value                                                                                                                              |
|------------------|------------------------------------------------------------------------------------------------------------------------------------|
| Algorithm        | HMAC-SHA1                                                                                                                          |
| Digits           | 6                                                                                                                                  |
| Time step        | 30 s                                                                                                                               |
| Secret encoding  | Base32 (20 random bytes)                                                                                                           |
| Provisioning URI | `otpauth://totp/<vault_id>?secret=<base32>&issuer=TTL-Legacy&algorithm=SHA1&digits=6&period=30`                                    |
| Replay protection| Each time step may be consumed once per vault; an older-or-equal time step is rejected                                             |

#### SMS / email OTP parameters

| Parameter      | Value                                            |
|----------------|--------------------------------------------------|
| Code format    | 6 decimal digits                                 |
| Expiry         | 300 s (5 minutes)                                |
| Pending store  | In-memory, per vault; expired entries pruned on verify |

#### At-rest encryption & key rotation

- Secrets are encrypted with an HMAC-SHA1 keystream (HMAC-CTR) keyed by
  `TOTP_ENCRYPTION_KEY`; a 16-byte random nonce is stored alongside the
  ciphertext under the `enc:v1:` prefix.
- Legacy plaintext secrets (pre-migration) remain readable transparently.
- `migrate_plaintext_secrets(db)` re-encrypts any legacy plaintext secrets
  under the current key; call it once after enabling `TOTP_ENCRYPTION_KEY` on a
  deployment that previously stored plaintext.
- To rotate the encryption key without re-enrolling authenticators: set
  `TOTP_ENCRYPTION_KEY_PREVIOUS` to the old key and `TOTP_ENCRYPTION_KEY` to the
  new key, then call `POST .../2fa/rotate-key` per vault. The secret value is
  preserved; only the ciphertext changes.

#### Backup codes

Single-use backup codes for account recovery when the authenticator device is
lost are **not yet implemented** in `two_factor.rs`. When added, the planned
endpoints are `GET /api/vaults/{vault_id}/2fa/backup-codes` (list unused codes)
and `POST /api/vaults/{vault_id}/2fa/regenerate-backup-codes` (issue a fresh
set, invalidating the old). They will be documented here once implemented.

### Error codes (2FA)

All 2FA errors use the standard envelope `{"code": "...", "message": "..."}`.

| HTTP | `code`             | Returned by                                                                          |
|------|---------------------|--------------------------------------------------------------------------------------|
| 422  | `invalid_input`     | `enable` with missing `phone`/`email` for the chosen method                          |
| 401  | `unauthorized`     | `verify` with an invalid or expired code                                             |
| 404  | `not_found`         | `verify` / `rotate-key` when 2FA is not configured for the vault                     |
| 500  | `internal_error`    | `TOTP_ENCRYPTION_KEY` unset/under-length, decryption failure, or database error      |

Related codes returned by other endpoints that gate on 2FA:

| HTTP | `code`                  | Meaning                                                          |
|------|-------------------------|------------------------------------------------------------------|
| 401  | `two_factor_required`   | A protected endpoint requires a verified 2FA session             |
| 400  | `two_factor_not_enabled`| 2FA was expected but is not enabled for the vault                |

### Rate limits

The 2FA endpoints are subject to the backend's global rate limiter
(`backend/src/rate_limit.rs`), applied per client IP across all routes. When the
per-IP quota is exhausted the endpoint returns `429 Too Many Requests` with
`{"error":"rate_limit_exceeded"}` and a `Retry-After` hint.

| Setting          | Env var            | Default  | Notes                                                                                |
|------------------|--------------------|----------|--------------------------------------------------------------------------------------|
| Store backend    | `RATE_LIMIT_STORE` | `memory` | `memory` (per-process, dev-friendly) or `redis` (shared across replicas; requires `REDIS_URL`) |
| Redis URL        | `REDIS_URL`        | —        | Required when `RATE_LIMIT_STORE=redis`                                              |
| Trusted proxies  | `TRUSTED_PROXIES`  | (none)   | Comma-separated CIDRs whose `X-Forwarded-For` is trusted for client-IP extraction    |

A separate per-vault limiter guards check-in-style vault actions (one request
per window); it is independent of the 2FA endpoints themselves.

## Scheduler Behaviour

The background scheduler polls every 60 seconds. For each vault with stored preferences it:

1. Fetches the vault's TTL remaining (hours) from the Stellar RPC.
2. Compares against `hours_before_expiry`.
3. Fires reminders on the configured channels according to `frequency`:
   - `once` — fires exactly once when TTL enters the window.
   - `daily` — fires every 24 hours while inside the window.
   - `hourly` — fires every hour while inside the window.

Preferences are stored off-chain in the backend SQLite database and are never written to the Soroban contract.

## Configurable Countdown Notifications

### `set_countdown_config`

```rust
set_countdown_config(vault_id: u64, caller: Address, thresholds: Vec<u64>)
```

Sets the countdown notification thresholds for a vault. Only the vault owner may call this. Each threshold is a number of seconds before expiry at which `check_countdown` will emit a `cd_notif` event. Pass an empty vec to disable notifications. Calling this also clears any previously fired threshold flags, so all thresholds will fire fresh on the next countdown cycle.

**Errors**

| Error     | Code | Condition                    |
|-----------|------|------------------------------|
| `NotOwner`| 6    | Caller is not the vault owner|

**Event emitted:** `set_cd` — `(thresholds)`

---

### `get_countdown_config`

```rust
get_countdown_config(vault_id: u64) -> CountdownConfig
```

Returns the countdown config for a vault. If not explicitly set, returns the default thresholds: 604800 (7 days), 259200 (3 days), 86400 (1 day).

---

### `check_countdown`

```rust
check_countdown(vault_id: u64) -> u64
```

Checks the vault's remaining TTL against its configured thresholds and emits a `cd_notif` event for each threshold that has been crossed since the last check-in or config reset. Each threshold fires **at most once** per countdown cycle. Fired flags are cleared automatically when the owner calls `check_in` or `set_countdown_config`.

Can be called by anyone — intended for off-chain keepers, cron jobs, or reminder services.

**Returns** the remaining TTL in seconds (0 if expired or vault is not Locked).

**Event emitted:** `cd_notif` — `(threshold_seconds, ttl_remaining)` — one per newly crossed threshold.

---

### `CountdownConfig` type

```rust
pub struct CountdownConfig {
    /// Sorted descending list of thresholds in seconds.
    /// Default: [604800, 259200, 86400] (7d, 3d, 1d)
    pub thresholds: Vec<u64>,
}
```

### Integration example

An off-chain keeper calls `check_countdown` on a schedule (e.g. every hour). When the vault TTL drops below a threshold, the contract emits a `cd_notif` event. The keeper reads the event and dispatches email/SMS/push reminders via the backend reminder service.
